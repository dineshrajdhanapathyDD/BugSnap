# Findings and lessons from building BugSnap

What I hit while building and testing this on a real account, in the order it mattered. "Measured" means I saw it in CloudWatch or an error message; "reasoned" means it follows from AWS behaviour but I did not benchmark it.

## 1. Express + `StartSyncExecution` gives a clean API contract

An Express workflow called with `StartSyncExecution` returns the final output, status and any error in one response. CreateBug can answer `201` with the bug ID and priority, or `400` with the validation messages, with no polling. A Fail state's `Error` and `Cause` come back in the response, so `Cause` carries the list of validation errors as JSON.

Trade-off: Express executions are only browsable in the Step Functions console because logging is enabled on the state machine (`Level: ALL`). The console's Executions tab then lists each run with its status and duration (see `docs/screenshot/05-step-functions-executions.png`). Turn logging on from day one or Express runs are hard to inspect.

## 2. JSONata keeps the state machine small

With `QueryLanguage: JSONata`, `Arguments` and `Output` take the Lambda payload straight through (`{% $states.result.Payload %}`), the Choice is one expression (`{% $states.input.valid = true %}`), and the Fail cause is `{% $string($states.input.errors) %}`. No ResultPath/OutputPath juggling.

## 3. Validation rejections count as failed executions (measured)

Over my test runs Step Functions reported 38 started, 31 succeeded and 7 failed. All 7 were deliberate invalid submissions. The `ExecutionsFailed` metric cannot tell a rejected input from a crash, so an alarm on it would page on user mistakes. Better: end rejected input with a Succeed/Pass state carrying `valid: false`, or alarm on Lambda errors and `ExecutionsTimedOut` instead. My alarm threshold is 5 failures in 5 minutes; that is a known compromise.

## 4. CloudFormation does not republish an API Gateway deployment (hit, then fixed)

After adding methods and changing CORS, the live API kept the old behaviour. An `AWS::ApiGateway::Deployment` is not recreated when only the methods change, and changing its description only updates the description. My tests showed the stale CORS headers. Fix: `scripts/deploy.ps1` suffixes the deployment's logical ID with a hash of the template, so any change creates and attaches a new deployment.

## 5. DynamoDB allows one new global secondary index per stack update (hit)

Adding two GSIs to an existing table failed with "Cannot perform more than one GSI creation or deletion in a single update". A new table can be created with both. For an existing table, add them in two deploys, and wait for the index status `ACTIVE` (backfill) before shipping the code that queries it.

## 6. Replacing Scan with GSIs changes the cost shape (reasoned)

Listing is now a handful of Query calls on `status` / `severity` + `created_at`, newest first, instead of reading the whole table. The price is write amplification: every item write is also written to each index that includes it (about 10 write units per bug over its life, see the cost analysis). And the COUNT queries behind the dashboard stats still read data in proportion to table size. For a larger app, keep counters.

## 7. The 128 MB default is fine for these functions (measured)

Average durations: Validate 5 ms, Get/Save/Prioritize about 100 ms, CreateBug about 400 ms (it waits for the workflow). The slowest CreateBug call was 3.0 s, which was a cold start. For a bug tracker this is acceptable; if first-request latency mattered I would move to ARM and trim imports.

## 8. Browser CORS has more places than the Lambda response

Four separate places needed the origin: the Lambda responses, the API Gateway OPTIONS mock integrations, API Gateway's own error responses (a 4xx or 429 generated by the gateway has no Lambda to add headers), and the attachment bucket's CORS rules for the direct screenshot upload. I added `GatewayResponse` resources for `DEFAULT_4XX` and `DEFAULT_5XX` so throttling errors are readable by the browser.

## 9. Private by default, public only where unavoidable

- The screenshot bucket is fully private; uploads and downloads use 5-minute presigned URLs. The tests assert a direct request returns 403.
- The first version served the site from a public S3 website bucket (HTTP only). I moved to CloudFront with origin access control: HTTPS, security headers, and a bucket that is no longer public (a direct request returns 403).

## 10. I tried Cognito and took it out

I added Cognito sign-in with an API Gateway authorizer (it worked, and the test suite grew to 37 checks) and then removed it to keep the project a small app that runs end to end. The result is an open API, protected only by throttling. That is the main limit of this build and it is stated in the README. The upgrade path is short: a user pool plus a Cognito authorizer on the five methods; CloudFront already provides the HTTPS callback URL.

## 11. Do not take over account-wide settings

API Gateway's CloudWatch logging role is an account-level setting that another stack already owned. The template does not create `AWS::ApiGateway::Account`, so deploying or deleting BugSnap cannot change that role. Access logs work because the role is already configured. Anyone deploying into a fresh account needs to set it once.

## 12. Tests against real resources caught what review missed

The end-to-end suite (29 checks, run against the deployed stack) is what exposed finding 4. Mocked tests would have passed. It also verifies the security claims (private buckets, HTTPS headers, CORS) instead of trusting the template.

## What I would do next

1. Add a Cognito authorizer (finding 10).
2. Replace COUNT queries with maintained counters (finding 6).
3. Return rejected input as a successful workflow result so alarms mean something (finding 3).
4. Add pagination tokens to `GET /bugs` instead of the 200-item cap.
